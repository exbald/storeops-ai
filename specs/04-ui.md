# User interface contract

The UI is part of each integration gate. An API-only backend and static dashboard do
not constitute the complete MVP. Use generated TypeScript types/client from OpenAPI.
All normal data access passes through the API; local fixtures must never be bundled
as the application data source. Mock Service Worker is permitted only in isolated tests.

## Routes and required behavior

| Route | Role | Required interactions |
|---|---|---|
| /sign-in | Member | Firebase sign-in; meaningful unauthenticated/unprovisioned states; no bespoke password storage |
| /setup | ADMIN | Empty-workspace checklist linking to stores, catalog, imports and approved policy; counts come from persisted records |
| /stores | Both | Search/filter stores; show opportunity proxy or “Needs data”; create/edit/archive available to admins |
| /catalog | ADMIN | Product CRUD, archive safeguards, case size and reference image upload; distributor location management |
| /imports | ADMIN | Choose sales/stock CSV, preview validation totals/errors, explicitly commit, view history and correction outcome |
| /promotions | ADMIN | Create/edit a draft, select stores/dates, upload agreement, trigger extraction, inspect pages and edit/approve rules |
| /stores/:id | Both | Real sales/stock freshness, visit history and readiness; begin a visit; no invented default metrics |
| /visits/:id | Both | Notes, before/after uploads by zone, investigation progress, evidence links, plan acceptance and verification |
| /investigations/:id | Both | Deep link to hypothesis, alternatives, snapshot, tasks, ordered events and immutable attempts |
| /reports/:id | Both | Saved verification report; before/after evidence and per-rule outcomes; printable browser view |

## Empty states and task flow

An empty workspace shows setup guidance, not sample stores. No sales is “No sales data”,
not zero sales. Missing stock is “Stock unknown”, not out of stock. A null opportunity
proxy is “Insufficient comparison data”, not SGD 0.00. Show timestamp and source beside
every stock figure. Distributor and store stock always have separate labels.

The rep flow is store → open visit → upload → investigate → inspect → accept → perform
work → upload after evidence → verify → report or specific remaining checks. Show the
accepted plan revision and current policy status. Do not let stale buttons issue writes
without handling VERSION_CONFLICT and refreshing current state.

## Progress and errors

Poll /jobs/:id and /jobs/:id/events with the last sequence; start at 1 second, then 2–5
seconds while queued/running, stopping at terminal state. Persist job/resource IDs in the
route, not only component memory. Distinguish queue delay, active processing, provider
failure and a valid inconclusive result. Retry creates a visible linked attempt.

Disable duplicate submission locally, but rely on server idempotency for correctness.
Explain row-level import problems and preserve the original file/result. Upload progress
and processing progress are separate. Never show fabricated tool animation as a live run.

## Evidence and accessibility

Evidence opens the exact PDF page/span, image region or source-row details; use durable
evidence IDs with freshly fetched download URLs. Render normalized bounding boxes against
the displayed image dimensions. Labels include product names and observed/required counts.

At 375 px and desktop widths, the main flow has no horizontal page overflow. Inputs have
labels, focus states, keyboard operation and text equivalents for status colors. The
report says “Execution verified” only after PASS; causal or sales-recovery claims are not
part of verification. A visible local/stub/recorded banner must never appear on an app
claiming live cloud acceptance.
